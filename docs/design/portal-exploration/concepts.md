# 通讯 · 效率 · 任务：概念整理与深度设计

> 探索稿。七版界面都被否之后，停止画界面，先把三个词的定义和边界钉死。
> 这一版不产出页面，产出的是**判据**：以后任何界面都要满足这里的定义。

## 0. 结论

这三个词不是三个功能，也不是三个页面，是**同一条链路上的三层**：

```
通讯（发生什么） → 效率（把发生的事变成可操作的东西） → 任务（要我做/它要做的事）
       ↑                                                        │
       └──────────── 所有动作回写通讯，留下痕迹 ────────────────┘
```

界面做成什么样是次要的。**只要这三层的关系对，微信式三栏、指挥台、手机推送都是同一个产品的不同视图。**

## 1. 通讯（Communication）

**定义**：一段可回溯的、带参与者与时序的记录。在这个项目里就是 `rooms.json` 的 `transcript`（私聊是 `sessions.json` 的 `messages`）。

它有四个不可让渡的属性：

| 属性 | 含义 | 违反的后果 |
|---|---|---|
| 时序 | 按 `at` 排，不按 UI 分组重排 | 用户无法判断“它是在我回复之前还是之后说的” |
| 参与者 | 每条有明确 speaker（user / bot / system） | 分不清谁说的，责任消失 |
| 可回溯 | 写出去的东西能找到原始行 | 出问题无法复盘，Bot becomes untrustworthy |
| 带钩 | 需要后续动作的行带 `task_sig` | 长任务滚出 200 条后彻底丢失 |

**关键约束**：transcript 只保留最后 200 条，是**存储现实**，不是设计选择。所以任何只依赖“翻消息”的界面，在长任务上必然失效。这是历次设计里最容易犯的错。

**通讯层不负责**：状态判断（“跑完了吗”）、权限（“能不能发”）。它只记录事实。

## 2. 任务（Task）

**定义**：一个**显式状态实体**，有 id（`task_sig`）、状态、负责人、起点时间和待决问题。在这是 `tasks.json`。

它和通讯的本质区别：

| | 通讯 | 任务 |
|---|---|---|
| 形态 | 流，会滚走 | 实体，一直在 |
| 状态 | 隐含在最后一条消息里（要猜） | 显式字段 waiting / running / done |
| 生命周期 | 无限 | 有开始、有结束、有取消 |
| 能否操作 | 不能 | 能：刹停 / 改向 / 换人 / 批准 |

**三条硬规矩**（现在是代码事实，不是愿望）：

1. **一个 `task_sig` 只有一张卡**。之前出过两次的 bug：合并顺序错 → 同一任务在指挥台出现两张卡，用户点哪张都不对。
2. **状态以 Task 实体为准，不从 transcript 推**。实体是显式的；转录是历史的。推就会错。
3. **每个 “waiting” 必须带一个可回答的问题**。“等你输入”不算问题；“三条路断了，选 A/B/C 或给我一个输入”才算。

**任务层不负责**：消息长什么样、用什么语气。它只管“这件事到哪了、卡在哪、谁该动”。

## 3. 效率（Efficiency）—— 是桥，不是页面

**定义**：把通讯变成任务、再把任务动作写回通讯的那一层。在这个项目里是 `hosts/shared/task_view.js` + desktop/mobile 的指挥动作。

它做的三件事：

1. **聚合**：`aggregateCommandTasks(rooms, taskRecords)` —— 从 transcript 建卡，再用 Task 实体覆盖状态。
2. **去重与补全**：转录滚掉了但实体还在的，补一张「仅记录」卡；同一 sig 不重复。
3. **跨端一致**：桌面指挥台和手机 `/v1/tasks` 调**同一个函数**。这是已定的红线，不许出现第二份聚合逻辑。

**效率不产生新信息**。它只做一件事：让用户**不必从消息流里手工重建状态**。凡是让用户“翻记录拼出当前状态”的界面，都是效率层的失败，不管多好看。

**效率的判据只有一条**：

> 从“我看到一件事”到“我做完一个动作”，中间有几步？
> 每一步跳转都是损耗。目标是 0 跳——在消息发生的地方就能操作。

## 4. 三者之间允许/不允许的转换

| 转换 | 允许吗 | 规则 |
|---|---|---|
| 通讯 → 任务 | ✅ | 只有带 `task_sig` 的行才能成为任务；不能从普通消息猜出任务 |
| 任务 → 通讯 | ✅ | 每个动作（批准/刹停/改向/换人/取消）必须写回一条可审计转录行 |
| 任务 ↔ 任务 | ✅ | 改向 = 旧任务作废 + 新 sig；不能就地改状态冒充“一直在做” |
| 通讯 → 通讯 | ✅ | Bot 回复；但要标明它与哪个任务相关（有 sig 就带） |
| 效率 → 任何 | ❌ | 效率层不写盘、不改状态。它是只读的视图与动作转发 |

最后一条最关键：**聚合层不能变成第二个数据源**。一旦它开始自己记状态，桌面和手机就会分叉，而分叉之后没人知道该信谁。

## 5. 由此推出的界面判据（不指定长什么样）

任何界面，无论是三栏、指挥台、手机推送、还是别的：

1. **能看到状态**：一屏之内能回答“现在哪些事在等我、哪些在跑、哪些卡住了”。
2. **不要求翻记录**：状态来自 Task 实体，不是让用户从最后 200 条消息里数。
3. **就地操作**：看到卡住的那条消息时，操作按钮就在它旁边；跳到别的面板才算失败。
4. **动作留痕**：任何指挥动作之后，transcript 里多一条带 `task_sig` 的记录，能被事后查到。
5. **跨端同屏**：桌面和手机看到的同一 `task_sig` 状态必须一致（同一个 `task_view.js`）。
6. **模板是入口不是主角**：模板决定 Bot 的边界（能不能发、能不能改配置），但用户面对的是任务，不是模板清单。

## 6. 当前断在哪（诚实清单）

| 断点 | 表现 | 该谁补 |
|---|---|---|
| 消息里的“等我”不总是变成任务卡 | 用户看到 Bot 说“给我一个输入”，但指挥台没卡 | 写端：确认请求要落 `tasks.json` |
| 桌面卡住要靠另开面板 | 通讯与任务在两个 UI 里，用户在中间来回跳 | 界面层：就地操作（判据 3） |
| 手机能看能指挥，桌面要开面板 | 同一状态两个入口，但路径不同 | 界面层：统一入口，不是统一数据 |
| 模板边界没进体验 | 模板文字写着“未批准不发送”，界面上不体现 | 体验层：把边界显示成看得见的承诺 |
| 长任务滚出 200 条 | 修复靠「仅记录卡」，但用户不知道那是同一件事 | 效率层：补卡时标明“原消息已滚出” |

## 7. 为什么这一版不画界面

七版界面都被否，说明问题不在布局、不在参照系（微信/OpenClaw 都试过了），
在于**没有先说清这三件事是什么关系**。关系没定，画什么都是猜。

这一版把关系定下来。下一步无论画什么，先过 §5 的六条判据——
过不了的，不管多像微信、多像一个一人公司驾驶舱，都不做。
